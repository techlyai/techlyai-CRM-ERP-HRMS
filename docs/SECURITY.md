# Security and verification

All business reads and writes require a fresh database-backed session. User IDs come from opaque session tokens, never browser-submitted identity fields. Passwords use individual random salts with Node.js scrypt. Session hashes are stored in a private table; logout revokes the current session, password changes revoke other sessions, and account deactivation blocks current sessions immediately on the next request. Initial administrators must change their generated passwords before accessing business modules.

The application role has RLS-constrained reads and only explicitly allowed transaction functions. Ordinary writes cannot directly modify attendance timestamps, stock counts, leave balances, payment totals, or approval states. Private HR/payroll/attendance records remain restricted even with overbroad employee grants. Managers start without module access. DB roles do not come from browser metadata.

The service role is available only inside trusted server code for session validation, provisioning, scheduler execution, and file handling. Its database credential is highly privileged within the application's data; do not distribute it to clients. Keep the migration-owner URL off the deployed app, use verified TLS for remote databases, and limit database network access. The database migration establishes no publicly reachable API.

File upload and completion endpoints check same-origin requests, current sessions, record visibility/upload permission, size, extension, MIME, and magic bytes. Chunks are bounded to 3 MiB; unfinished uploads expire in an hour, with a 100 MiB/20-upload per-user staging quota. Final files and metadata commit together. Downloads and custom sounds require a current authorized session. File signatures do not replace antivirus scanning.

GPS is device-reported and is collected only during attendance actions with user consent. Geofence/accuracy flags aid review but do not prove physical presence. No background location tracking is implemented.

Before release, run the SQL integration suite against an isolated PostgreSQL database, exercise the application with separate admin/manager/employee accounts, and test concurrent stock/leave/payment writes. Verify session revocation, document permissions, full-size uploads, push delivery, scheduler authentication, and backup restoration. Upgrade/audit the cached Next.js dependency before production deployment. Passing a build and unit tests does not establish database or production correctness.

## Usernames and development accounts

People can sign in with a username or their phone number; both are looked up server-side and share the same rate limits and error message. Usernames are lowercase, unique, and changed through `set_profile_username`, which applies the same reach rules as editing a profile. Administrator password resets go through `authorize_password_reset`: Super Admins may reset anyone else, Admins only people they can edit (never Super Admins), and nobody resets their own password this way. A reset generates a random temporary password shown once, forces a change at next sign-in and revokes the person's sessions.

`npm run seed:dev-accounts` creates shared test accounts with a weak password for local work. Those accounts are marked `weak_password`; with `NODE_ENV=production` the server refuses them after password verification unless `ALLOW_DEV_ACCOUNTS=true`, and the seed itself refuses to run. `docker-compose.yml` does not pass `ALLOW_DEV_ACCOUNTS`, so production deployments cannot enable them by accident. Any password change clears the flag. No credentials are stored in the repository or sent to the browser.

## GPS attendance and geofencing

Check-in and check-out read the device position once, when the person presses the button (or "Check my location"); nothing is collected in the background. The server, not the browser, decides whether a position is verified: `clock_attendance` compares it with the stored coordinates and radius of the person's assigned office (`attendance_assignments`, otherwise the default office) and records the distance, reported accuracy and result. A position is verified only when it is inside the radius and its reported accuracy is no worse than the radius. Offices that "refuse check-in outside the geofence" reject unverified check-ins; others record them as not verified. Check-out is never refused, so leaving the office cannot create a missing check-out; its result is recorded for review. Work-from-home check-ins outside the geofence need a per-person allowance.

Browser GPS can be spoofed, so a verified result shows what the device reported, not proof of presence. Attendance rows can only be written through `clock_attendance` and the correction workflow; an approved correction keeps the original times on the record. Employees see only their own records and office. Admins see others' attendance only within their attendance view scope. Office coordinates, radius and assignments change only through `save_office_location` and `set_attendance_location`, which require the separate `locations.manage` and `locations.assign` permissions (Super Admin only by default); every change is written to `location_audit`. Exact coordinates are removed after the retention period (default 365 days) by the scheduler; distance and verification results remain. Serve the app over HTTPS: browsers only provide location to secure origins.

## Field operations and GPS photos

Field tracking applies only to people a Super Admin (or someone granted `field.manage`) turns on in Field operations → Settings; everyone else uses normal attendance. Team Leader is an assignment on each field employee, not a role. Seeing another person's field data needs the `field.view` permission **and** either an assignment link (Team Leader, Reporting Admin or authorized viewer) or a Team/Department/All scope that reaches them; reviewing photos needs `field.review`, approving reports `field.approve`, exporting `field.export`. Nothing is granted by default. All of this is enforced by row level security and `private.field_allowed`; Employee-role Team Leaders read names through `public.field_people`, which exposes only name, employee ID, department and role.

Location is collected only during a field session the employee starts, inside the scheduled window, after an attendance check-in. Browsers only report location while the Orbit page is open, so the app samples a point per configured interval while open and queues points offline; it does not claim continuous background tracking, and the route shows gaps. The server rejects points outside the session window, deduplicates retries by a device-generated id, throttles bursts, and stops accepting points when the session ends (by the employee, at attendance check-out, at the scheduled end, or when an administrator turns tracking off).

GPS photos are stored in private storage and served only through `/api/field/files/…` after a row level security check, with `Cache-Control: private, no-store`; there are no public URLs. The original file is kept as uploaded (including any EXIF), but EXIF is never used for verification. A photo is "Verified – Within Geofence" only when it was taken with the camera during the session, the reported position is inside the expected site's radius, the reported accuracy is no worse than the radius, and the device capture time is within the configured tolerance of server time. Gallery images, missing expected sites, missing/inaccurate GPS and time differences go to manual review. These checks describe what the device reported; they cannot prove presence or detect every spoofed location or edited image. In-app notifications go to the Team Leader and Reporting Admin (Super Admins when neither can view); notification text and emails never contain coordinates. Configuration changes are recorded in `field_audit`, reviews in `field_events`. Tracked points older than the retention period are deleted and photo/visit coordinates cleared by the scheduler.

## Client credentials vault

Client logins are stored on the client record's Credentials tab. Passwords are encrypted on the application server with AES-256-GCM before reaching PostgreSQL; the key is `CREDENTIALS_ENCRYPTION_KEY` (32 random bytes, 64 hex characters) and never enters the database or the browser. Each ciphertext is bound to its credential and version, so it cannot be moved between records. To rotate, set a new key and list previous keys in `CREDENTIALS_PREVIOUS_KEYS`. Back up the key separately from database backups: without it, stored passwords cannot be recovered.

- **Access.** Listing, adding, editing and revealing current passwords require Edit access to that client. Opening previous passwords requires Super Admin or Approve access to clients, plus re-entering the user's own password (valid for 10 minutes). Permanent deletion is Super Admin only, after archiving, with a reason.
- **History.** Every password change closes the previous version and stores the new one in a single transaction. Versions keep who set and replaced them, when, and why.
- **Audit.** Creation, edits, password changes, reveals, copies, history views, archive, restore and deletion are recorded in `public.credential_audit` without any secret values. Reveals and copies are limited to 30 per user per minute.
- **Exposure.** Credentials are excluded from exports, global search and notifications. Passwords are fetched only when a user clicks Show or Copy, and revealed values are masked again after 30 seconds.

## Roles and permissions (migration 006)

Three access levels: **Super Admin** (`super_admin`, always full access), **Admin** (`manager`) and **Employee** (`employee`). Admins and Employees have only what their role defaults and individual overrides grant.

- **Catalogue.** Every grantable permission is a row in `public.permission_definitions` (module + action), referenced by `permission_grants` through a foreign key. The Settings → Roles & permissions checklist is generated from this table, and each item maps to a database check: business-record actions via `private.permitted`, plus Users, Settings, Audit, Chat and Client credentials permissions via `private.has_feature`/`private.credential_allowed`.
- **Scopes.** Record permissions reach Own records, Reporting team, Department or All records. Employees never reach other people's private HR records (employees, payroll, attendance, leave, corrections, onboarding), whatever they are granted.
- **Resolution.** `private.scope_for` returns the individual override if one exists, otherwise the role default, otherwise no access. Changes are read on every request, so revocations apply immediately.
- **Delegation.** Super Admins can change anything. Others need *Manage employee permissions* for the target person, can only grant or remove permissions within their own reach (`private.scope_covers`), cannot edit themselves or a Super Admin, and cannot change roles. Only Super Admins create Admins or Super Admins; Admins with *Create employee accounts* create Employees placed under them (team) or in their department.
- **Role defaults.** Super Admin only. A change applies either to everyone who inherits the default or to new people only, in which case existing people keep their current access as recorded overrides.
- **History.** `public.permission_audit` records every grant, revocation, reset, copy, template application and role-default change with before and after values, the actor, time and reason. No secrets are logged.

`scripts/verify-rbac.ts` exercises these rules against a database (`DATABASE_ADMIN_URL=… node scripts/run-ts.cjs scripts/verify-rbac.ts`).
